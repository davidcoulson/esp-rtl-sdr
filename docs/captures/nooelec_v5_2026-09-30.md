# Nooelec NESDR SMArt v5: first-party PC capture evidence, 2026-09-30

This document records the completed September 30 Pacific-time PC campaign and
the register evidence used by the internal Nooelec profile. It does not record
ESP32-P4 or OrcSDR hardware acceptance. Device recognition, PC control traffic,
PC IQ, host tests, an ESP build, flashed firmware, and physical reception are
separate results.

The implementation comparison uses `origin/master` at `105caa5`, the affected
release `v0.9.1`, and the `codex/nooelec-v5-profile` branch. The remote tag
`v0.9.1` peels to `105caa56b9b5ce395a7b4910c6f703c14b83b5d9`; the user
confirmed OrcSDR used that latest driver tag. Older Blog V3c, V4, and V4L evidence remains
specific to those boards unless the Nooelec captures independently reproduce
the relevant programming. No foreign driver source was copied or used to
derive the implementation. The vendor DLL was exercised through its public
API as a black-box PC reference.

## Initialization, matched IF, and board-specific filter bytes

Nooelec initialization matches the existing R820-family slice
`kRtlInitTransfers[363..419]` in `private/transfers_blog_v4.hpp` after remapping
the tuner address from `0x74` to `0x34`. Of its **57 transactions**, exactly
two write payloads differ: index **392** and index **409** write tuner
`reg0a=d3` on Nooelec, whereas the existing table writes `d5`.

The comparison includes requests, values, indices, lengths, OUT payloads,
read placement, and ordering. IN response payloads are observations rather
than fixed expected request bytes. Exact sequence anchors in
`verified\controls-decoded.txt` are:

| Operation | Frames | Nooelec `reg0a=d3` frames |
|---|---|---|
| Initial open, spanning `open_control` and `tuner_type` | 797–909 | 855, 889 |
| Direct-to-native transition at 24 MHz | 1765–1877 | 1823, 1857 |
| Explicit direct disable / reinitialization | 5801–5913 | 5859, 5893 |

The completed cold state is `reg05=83`, `reg07=75`, `reg0c=f0`,
`reg0a=d3`, `reg0b=6b`. The standard demod IF bytes are **38 11 12**:
under a nominal 28.8 MHz reference they decode to approximately
3,569,993.591 Hz. The cold PLL calculation must use the corresponding
**3.57 MHz** offset. The Nooelec cold FM sweep independently confirms that
pair; it is no longer an assumption from V3c similarity.

Returning from Q direct sampling to the tuner restores the `d3/6b` filters and
standard IF before native tuning. Entering Q mode deliberately puts the tuner
into standby, including `reg0a=36`; that standby byte must not be changed by
the `d5→d3` / `c5→c3` board mapping. V3c retains its older `d5/6b` boot policy.

The manufacturer's NESDR SMArt v5 specification describes approximately
**0.1–25 MHz direct sampling** and **25–1750 MHz tuner coverage**. The branch
claims overall RF request bounds **100,000–1,750,000,000 Hz**, follows the
measured PC route cutoff, and documents the unverified 24–25 MHz boundary.
It must not advertise every requested frequency as physically accepted simply
because it lies within those software bounds. The board has **no bias tee**
and **no V4 HF upconverter**. Manufacturer reference:
[Nooelec NESDR Series](https://support.nooelec.com/hc/en-us/articles/360005805834-NESDR-Series).

`verified\gain-register-map.csv` contains all rows for both 96.1 and 1.28 MHz.
The 1.28 MHz direct-Q requests preserve the same low-nibble ladder, but write
standby upper bits `b0..bf` and `20..2e`, with `reg0c=28`. Tuner writes while
the tuner is bypassed do not establish controllable analog HF gain. The
Nooelec profile must expose tuner gain only on the tuner route, rather than
turn those HF API returns into a gain capability claim.

Tuner AUTO and RTL AGC are separate controls. Tuner AUTO preserves the current
low gain nibbles, clears register-05 bit `0x10`, sets register-07 bit `0x10`,
and writes `reg0c=6b`. It does not reset the nibbles to zero. Controls frames
**3983/3985/3987** show **8f/7e/6b** after maximum manual gain; frames
**4011/4013/4015** show **80/70/6b** after a manual reset. Cold cached
defaults are **83/75**. Manual mode uses `reg0c=68`; the captured API switch
then resets the manual pair to **90/60**. Preserve the selected manual gain
when composing later profile state, rather than mistaking a mode toggle for
an RF gain calibration.

RTL AGC writes page-0 register-19 **05 off /25 on**, each followed by the
page-0a register-01 settle read. Controls frames **4035–4045** independently
show off/on/off. Tuner AUTO should not implicitly toggle RTL AGC.

## Affected v0.9.1 release and OrcSDR's 97.3 / 99.1 MHz displacement

The user reported hearing the 99.1 MHz station while OrcSDR displayed
97.3 MHz and confirmed the latest driver tag was in use. The remote latest
tag is verified as `v0.9.1`, at commit
`105caa56b9b5ce395a7b4910c6f703c14b83b5d9`. The exact OrcSDR image hash,
configuration, and on-device USB/register trace were not supplied. This
campaign did not reproduce the condition on ESP.

The PC oracle pairs both paths correctly. At 97.3 MHz, cold tuning gives
PLL LO about **100.870038 MHz** and demod IF **3.569994 MHz**. Explicit
bandwidth AUTO gives LO about **99.114972 MHz** and IF **1.814996 MHz**.
At 99.1 MHz the corresponding LOs are approximately 102.670038 and
100.914972 MHz. Switching between those matched paths preserves RF.

There is also a concrete source-level mismatch in `v0.9.1` / master `105caa5`:
the Nooelec PLL offset is already **3,570,000 Hz**, while the replayed init
finishes with demod IF **3b f7 78** (approximately 1.815 MHz), and the Nooelec
demod-IF restoration hook returns zero. That pairing puts the effective RF
approximately **+1.755028 MHz above the requested dial**; a 97.3 MHz request
therefore corresponds to about **99.055028 MHz**. The sign and approximate
size agree with the user's report. This is a code-supported explanation of
that affected release's behavior and a strong explanation for the reported
device symptom. The actual device register state and repaired on-device
behavior still need USB/log/RF verification.

The branch restores the matched cold IF and reinitialization state and keeps
explicit AUTO's PLL/demod change in one transaction. Do not describe an older
opposite mismatch, PLL 1.815 MHz with demod 3.57 MHz, as this same cause; its
frequency displacement would have the opposite sign.
