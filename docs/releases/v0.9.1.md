# esp_rtl_sdr v0.9.1 — release notes

Released 2026-09-28. This is the first published release of the 0.9 series.

These notes are written in plain language on purpose. They explain what changed, what broke on
the way, what we still know is wrong, and who helped. The short technical list is in
[`CHANGELOG.md`](../../CHANGELOG.md).

## The short version

`esp_rtl_sdr` is the driver that lets an ESP32-P4 board (we test on the M5Stack Tab5) talk to
RTL-SDR USB radio dongles. **0.9.1 is a big step from the last published release (0.8.0-rc3):**

- The **RTL-SDR Blog V4L** is now recognised as its own dongle instead of being mistaken for a V3.
- The **V3c**, **V4L** and **V4** all have their gain, tuner AGC, RTL AGC, bias-T and tuner-bandwidth
  controls copied from what the official PC driver does, measured with a USB analyser.
- A new optional **direct HF route** lets the V4 and V4L listen to 24 to 28.8 MHz (CB radio, for
  example) without the built-in up-converter, which was letting a strong AM station show up as a
  ghost on a CB channel.
- Many USB reliability fixes: unplugging and replugging a dongle, swapping dongles, and two dongles
  sharing a bus all behave better.
- **The most important fix in this release:** on the V3c, V4L (and, by the same code, the V4),
  changing the *tuner bandwidth* used to shift the radio to the wrong frequency while the screen
  still said the right one. That is fixed and was tested on all three dongles. The full story is
  below.
- One more real bug was found by an automated code review and fixed too: a list of bandwidth
  choices could be read past its end on the direct HF route.

If you use the driver through OrcSDR, you do not need to change anything. The public API did not
change.

## Why is this 0.9.1 and not 0.9.0?

`0.9.0` was written up in the changelog on 2026-09-26 but was **never tagged or published**. Two
days later we found and fixed the frequency-shift bug below, in the same code. Publishing a
"0.9.0" that contains a known bug we had already fixed did not make sense, so the first published
0.9 release is **0.9.1**. It contains everything the 0.9.0 changelog entry describes, plus the
fixes here. There is no `v0.9.0` tag, on purpose.

We also wrote down, for the first time, exactly how version numbers are chosen and how a release is
made: [`docs/VERSIONING.md`](../VERSIONING.md). From now on, pre-release names use a dot
(`rc.1`, `beta.2`) so that they sort correctly, and applications that use this driver in a
release pin a *published release* of it, not a loose branch.

## What is new since 0.8.0-rc3 (September 15)

There were about 60 individual changes. Grouped by what they mean for you:

### New and better hardware support

- **V4L detected properly.** The V4L uses a different tuner chip (R828S) that answers like the V3's
  chip, so it used to be set up as a V3 with a direct-sampling mode it does not have. The driver now
  reads the dongle's name and identifies it correctly.
- **V3 / V3c streaming promoted from "provisional" to "soak-verified".** A V3 ran for 787 seconds at
  1.024 million samples per second alongside a V4 at 2.4 million, with no transfer errors and no
  rejected setup commands. Note for anyone chasing similar faults: the handful of "EP 0 STALL"
  messages during V3 setup are the driver testing which tuner chip is attached. They are expected
  and are not a sign of a bad setup table.
- **V3c starts up correctly from cold.** The cold-start fix landed in 0.8.0-rc3 (September 15), just
  before this window. A user had reported a V3 that showed only static in OrcSDR
  ([issue #93](https://github.com/hardcoreerik/OrcSDR/issues/93)); on the OrcSDR release that
  carried these initialisation fixes, the same user confirmed the V3 working with FM spectrum,
  audio, RDS and gain.

### Controls copied from the official PC driver

We plugged the dongles into a PC, ran the official RTL-SDR Blog driver, recorded the USB traffic,
and replayed the *behaviour* (not the code) on the ESP32-P4. That gave us:

- measured **gain** steps;
- **tuner AGC** and **RTL AGC** switches;
- **bias-T** on/off with a guard, so it is never left on by accident (off by default, off on stop,
  off when the dongle is re-attached);
- **live tuner bandwidth** (200 kHz up to 2.4 MHz) with automatic rollback if a step fails half-way;
- the **V4L HF route** (28.8 MHz up-converter path).

### The direct HF route (24 to 28.8 MHz)

Through the built-in 28.8 MHz up-converter, a strong AM broadcast station at frequency *f* also
shows up at 28.8 MHz minus *f*. With a good antenna, the 1600 kHz AM station was heard on CB
channel 20 (27.205 MHz). With the new *optional* direct route
(`esp_rtl_sdr_set_hf_direct_min_hz()`), the V4 and V4L tune that range directly and the ghost went
away on both, matching the V3c. It is off by default. We have not measured the direct-input
passband or CB sensitivity.

### USB reliability

- A dongle that dies mid-setup no longer leaks its handle, and closing a device is never attempted
  while a transfer is still in flight (that used to trip an assertion).
- A stalled data pipe now recovers instead of quietly ending the stream while still claiming to be
  streaming.
- A stream restart no longer leaks a whole pool of transfer buffers.
- The tuner's I2C repeater is opened before a hot retune.
- Two dongles can share a USB bus: each is claimed by exactly one handle, and probing skips devices
  another handle owns. Hub ports can be power-cycled.

### Speed

- The data path from USB to your code was reworked to be lock-free and to copy less.
- The driver no longer rewrites tuner registers whose value is already correct. (That optimisation
  was followed one day later by a fix for a V4 repeater/cache-coherence problem: it is a good
  example of a speed-up needing a correction.)

### Experiments that were tried and put back

Between September 24 and 25 we experimented with sample rates up to 3.6 million per second and ran
a series of diagnostic trials on the USB byte counters. Those diagnostics were added and then
reverted one by one, and **the production sample-rate ceiling was restored**. Nothing from that
experiment is in the release. We mention it so nobody wonders why the history looks messy.

## The big story: the frequency that moved when you changed bandwidth

### What you would have seen

On the OrcSDR radio, open RF Lab and press **NEXT BW** to step the tuner bandwidth. The screen kept
saying **96.1 MHz**, but the picture on the spectrum slid sideways, the station sounded detuned,
and one side of the spectrum looked cut off. Pressing a normal frequency step (or +100/-100 kHz)
snapped everything back. A reboot also fixed it.

On the V3c the error was about **95 kHz** (up at 200 kHz, down again when returning to AUTO). On the
V4L it was much larger: **-312, -5, +98, -124, -50 and +386 kHz** at successive bandwidth steps.

### Why the screen still said 96.1 MHz

Because the radio *was* still asked for 96.1 MHz. The tuner chip was set correctly. The mistake was
in the *second* stage: the RTL2832 chip inside the dongle has its own digital frequency setting (the
"IF word", three bytes written one after another). Our bandwidth code wrote those three bytes
back-to-back. The official PC driver, and our own start-up sequence, read a status register after
each byte. Without those reads, the chip ended up using the *new* first byte with the *old* second
and third bytes. That is a slightly wrong digital frequency, so everything appeared shifted.

We do not know *why* the reads matter inside the chip (whether they latch the value, flush it, or
just add a delay), so we do not claim to. We only know that adding them removes the shift on all
three dongles, and that the size of the shifts matched our "old bytes mixed with new bytes" model to
within a few kHz at every step.

### How we found it

1. **We built a test rig.** After every step it captures one second of raw radio samples from the
   dongle over the serial cable, checks the file against the device's own checksum, and measures
   where the station really is, how the two sides of the spectrum compare and whether any samples
   were dropped. That turned "it sounds wrong" into numbers.
2. **We recorded the official PC driver** doing the same bandwidth steps on the same V3c, with a USB
   analyser, and compared it with ours transfer by transfer. The PC stayed centred; ours did not. The
   big visible difference was the reads after each byte.
3. **We read the tuner chip's registers back** from the running dongle, which showed us the second
   bug (below), and proved the chip holds exactly what we write.
4. **We changed one thing at a time** and re-ran the same test after each change.

### The second bug (V3c only): AUTO left the passband narrow

After the shift was fixed, returning the V3c to AUTO bandwidth still left the left half of the
spectrum about 13 dB too quiet. Reading the tuner back showed why. When the V3c starts it runs a
recorded start-up sequence that leaves its filter registers at `d5/6b`. Our AUTO setting wrote
`c5/8f` instead. `c5/8f` is what the *PC driver* uses, but together with a different internal
frequency (1.815 MHz) than the V3c really runs at (3.570 MHz). So AUTO put the V3c into a mixed-up
state that neither the V3c's own start-up nor the PC driver ever uses. AUTO now restores exactly the
start-up state.

### Wrong turns and regressions, told honestly

- **Bandwidth programming was switched off on the V3c for a few hours** (September 27, as a
  first response to V3c tuning trouble with the 0.9.0 code). It was a workaround, not a fix, and it
  was re-enabled the same evening.
- **We tried replaying the complete tuner setup after every bandwidth change** (a candidate called
  `be7ff03`). It did not fix the shift and it made the left side of the passband *worse*. We tested
  it properly, saw that, and **rejected it**. It is not in this release.
- **The AUTO passband problem was our own regression.** It appeared on September 28 when we made AUTO
  restore the start-up frequency but left the PC driver's filter registers in place.
- **The frequency shift itself dates back to September 25**, when live tuner bandwidth was first
  added. It was there for the V3c and V4L; the V4 uses the same code, so we expect it was there too,
  but we never measured the V4 before the fix.
- **One of our first tests was invalid** because the test script mistook a Wi-Fi pause for the dongle
  being replugged, and the unplug landed in the middle of a capture. We fixed the script and reran.

### What we tested

Same station (96.1 MHz), same steps on every dongle: AUTO, 200 kHz, 300 kHz, 500 kHz, 1.0 MHz,
1.8 MHz, 2.4 MHz, AUTO. Once from a cold boot and once after unplugging and replugging the dongle.

| Dongle | Frequency error before | Frequency error now | Passband back to normal at the end |
|---|---|---|---|
| V3c | about +95 / -95 kHz | within +2 kHz | within 0.8 dB (one run 3.6 dB, then within 0.4 dB when repeated) |
| V4L | -312 to +386 kHz | within 2.5 kHz | within 0.5 dB |
| V4 | not measured | within 1.4 kHz | within 0.4 dB |

Every run also had: the asked-for bandwidth equal to the applied one, exactly one retune per step,
no radio restarts, no rejected setup commands, no USB overruns, and no dropped samples or audio.
The whole evidence set (logs, per-run reports, plots, checksums of the raw samples) is in the OrcSDR
repository (`hardcoreerik/OrcSDR`) under `docs/testing/evidence/v3c-tuner-bandwidth-2026-09-28/`, and the PC capture
analysis is in [`docs/captures/v3c_live_bandwidth_2026-09-28.md`](../captures/v3c_live_bandwidth_2026-09-28.md).

## Another bug found by code review

An automated reviewer (CodeRabbit) read the earlier 0.9.0 pull request and flagged a real problem:
the function that lists the available bandwidth choices decided *how many* to list with one rule
and *which list to read from* with a different rule. On a V4 or V4L using the direct HF route (CB at
27.205 MHz, for instance) it would report seven choices but read them from a list with only four,
so the last three were random memory. It is fixed by making both come from one function, and there
is a test that checks every choice offered is one the driver accepts. OrcSDR calls this function
to build its tuner-bandwidth choices.

## Known issues

We would rather tell you than have you find out:

- [#32](https://github.com/hardcoreerik/esp-rtl-sdr/issues/32): changing the direct-route threshold
  *while streaming* does not retune the tuner.
- [#33](https://github.com/hardcoreerik/esp-rtl-sdr/issues/33): a V4L bias-T change can overwrite the
  active route's GPIO bits.
- [#34](https://github.com/hardcoreerik/esp-rtl-sdr/issues/34): at exactly 28.8 MHz two rules
  disagree about which bandwidth list applies.
- [#35](https://github.com/hardcoreerik/esp-rtl-sdr/issues/35): if five device closes get stuck at the
  same time, the fifth is dropped.
- [#36](https://github.com/hardcoreerik/esp-rtl-sdr/issues/36): **Nooelec SMArt v5.** The tuner is set
  for a 3.57 MHz internal frequency but the demodulator is not put back to 3.57 MHz after start-up,
  the same kind of mismatch as above. A fix exists but has no hardware test. The Nooelec profile is
  still **provisional**: it has never been tested on a real Nooelec here.
- [#24](https://github.com/hardcoreerik/esp-rtl-sdr/issues/24) and
  [#25](https://github.com/hardcoreerik/esp-rtl-sdr/issues/25): a sample-rate bug in the low range
  and "no RF on a Nooelec". Proposed fixes are in [#26](https://github.com/hardcoreerik/esp-rtl-sdr/pull/26).
- **Not measured:** the real width of the tuner filters in Hz (the numbers are the PC driver's control
  values, not measured bandwidths), absolute gain accuracy, direct-route sensitivity, other stations
  and long soak runs of this exact build.
- The dongles ran on **one Tab5** (ESP32-P4 revision 1.3). Other boards are not verified.

## What was checked

- Host tests (Linux and Windows CI), the version/"truth" hygiene check, and a full ESP-IDF
  ESP32-P4 compile all pass.
- The frequency fix was tested on real V3c, V4L and V4 dongles as described above.
- Each of the three fixes has a new host test, and each test was confirmed to fail when its fix is removed.
- We do **not** claim a long-duration soak of 0.9.1 itself.

## Using it

Nothing to change in your code. `esp_rtl_sdr_get_version_string()` now returns `0.9.1`. If you pin
this driver, pin the commit of the `v0.9.1` tag (see [`docs/VERSIONING.md`](../VERSIONING.md)).
