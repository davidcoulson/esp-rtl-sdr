# esp_rtl_sdr v0.9.2 — Nooelec NESDR SMArt v5

Release date: September 30, 2026. This patch release completes the existing
Nooelec SMArt v5 driver profile from independent PC captures and fixes its
cold-start frequency mismatch. The public API and profile identifier are
unchanged. The maintainer explicitly selected version `0.9.2` and authorized
the `v0.9.2` tag after the implementation merged.

The Nooelec profile is implemented, checked against captured USB controls,
host-tested and compiled for ESP32-P4. **Reception with this driver on physical
ESP32-P4 hardware remains unverified.** PC reception and USB captures are separate
evidence from reception through the embedded driver. This release includes no
application integration, flashing or new hardware acceptance result.

## Why 99.1 MHz was heard at a 97.3 MHz setting

The maintainer reported that the Nooelec received the 99.1 MHz station only when
OrcSDR was tuned to 97.3 MHz, while using driver tag `v0.9.1`.
In that driver, the Nooelec tuner calculation used a 3.570 MHz intermediate
frequency, but shared initialization left the demodulator at about 1.815 MHz.
Those two internal frequencies must agree. Their difference produces an
effective RF shift of approximately +1.755 MHz: a 97.3 MHz request effectively
lands near 99.055 MHz. The sign and size agree with the reported station.

This is a source-supported explanation. The application's exact USB/register
trace was not recorded, so these notes do not claim a measured before/after
repair on the embedded device. Version 0.9.2 restores the independently captured
Nooelec cold filter state `d3/6b` and pairs both sides at 3.570 MHz. Changing the
sample rate and returning from HF restore the same required demodulator state.

## What the profile now does

| Operation | Behavior in 0.9.2 |
|---|---|
| Identification | Existing Nooelec manufacturer / NESDR SMArt v5 product descriptor profile on VID/PID `0bda:2838`; captured serial is provenance, not an allowed-device list |
| Cold native tuning | Nooelec `d3/6b` filters with matched 3.570 MHz tuner and demodulator IF |
| Manual native gain | All 29 nominal gain choices map to the captured tuner register pairs |
| Tuner AUTO | Uses the captured mode bits, preserves gain nibbles and remains applied across native retunes and bandwidth changes |
| RTL AGC | Independent demodulator controls with the captured write/settle-read pairs |
| Native tuner bandwidth | Seven requests at 2.4 MS/s with corresponding filters and matched IF changes |
| Explicit bandwidth AUTO | Uses Nooelec's independently captured `c3/8f`, 1.815 MHz plan; this differs from the cold state and the older V3c AUTO policy |
| HF Q sampling | Captured Q enable/disable and exact-Hz NCO below the PC's 24 MHz transition; native tuner state and explicitly applied gain/mode are restored on return |
| Tuner controls during Q sampling | Gain/mode and tuner bandwidth setters reject requests while the tuner is bypassed |
| Model bounds | 100 kHz–1750 MHz; this is a request range, not measured reception throughout that range |
| Bias tee / HF upconverter | Neither capability is advertised for this model |

Ordinary startup and native retunes do not silently choose the explicit
bandwidth AUTO plan. The gain stage caches follow captured single writes and
bursts, including reinitialization. Review also fixed a queued AUTO-to-MANUAL
change interrupted by an HF transition, so a successful manual restoration
cannot retain a stale AUTO-applied flag.

The manufacturer rates native operation from 25 MHz. The captured PC switches
from Q to native at 24 MHz, but the exact 24 MHz tune reported that the PLL was
not locked. This release follows the observed control transition without
claiming successful reception at that boundary. Gain values are nominal and
bandwidth requests are vendor control choices; neither is an analog calibration.

## Captures and provenance

The September 30 campaign used the same classes of stimuli and retained data
as the earlier Blog V3c, V4 and V4L work, and adds model-specific comparisons.
Seven accepted USBPcap parent captures contain 34,018 paired control submits
with zero unmatched completions. The 204 failed transfers are the four
absent-tuner probe operations across 51 opens; they are explicitly accounted for.

The data includes eleven cold FM frequency points, repeated identical tunes,
all 29 manual gain pairs, tuner/RTL AGC controls, seven bandwidth selections,
live bandwidth changes, eight HF Q points, longer gain holds and matched IQ
lengths. FM used the confirmed dipole. AM1280/AM1600 used the independently
powered MLA-30+ and external injector, including the requested ten-second
AM1600 audio recording. These describe PC reference reception, not an embedded
driver acceptance run.

The vendor DLL was exercised through its public API as a black-box reference.
No foreign SDR driver implementation was read, translated or imported for this
work. The retained raw data remains outside Git at
`C:\Tools\esp-rtl-sdr-lab\captures\nooelec-v5-20260930`.
All seven accepted parent PCAP hashes were freshly checked against the manifest.
A separate human-readable report/manifest discrepancy is recorded; no blanket
fresh rehash of all 163 retained artifacts or tool binaries is claimed.

See the [capture record](../captures/nooelec_v5_2026-09-30.md) for procedures,
USB/frame anchors, tool/device identities, hash tables and remaining gaps.
Older V3/V4/V4L records remain explicitly historical, model-specific evidence.

## Using the tag and remaining checks

`esp_rtl_sdr_get_version_string()` reports `0.9.2`. Existing callers keep the
same API. Consumers can identify the immutable commit behind the annotated tag:

```sh
git rev-parse 'v0.9.2^{commit}'
```

Application integration is a separate follow-up. Nooelec embedded enumeration,
station placement, native/Q transitions, gain/AGC behavior, bandwidth transitions,
hotplug and longer soak still need physical checks. Analog passbands, absolute
gain, rated range-edge reception and timing under USB failures remain unmeasured.
Prior Blog V3c/V4/V4L hardware results keep their original scope and do not
become fresh acceptance of this release simply because its version changed.
